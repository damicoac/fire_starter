AI pentesting.
From target to findings.

Fire Starter is an AI pentesting agent for web apps, APIs, and exposed services. Give it an authorized target; it discovers the attack surface, chooses security checks, and investigates potential vulnerabilities. Get a findings report and supporting evidence—without coordinating every tool by hand.

Less orchestration. More investigation.

Security testing is more than running a scanner.

Discovering endpoints, choosing the next check, keeping a session alive, and assembling the results all take work. Fire Starter connects those steps in one autonomous assessment workflow.

Stop coordinating every tool by hand.

The agent chooses from built-in security tools using what it has learned about the target. Discovery results feed the next checks, so you spend less time moving context between separate tools.

Investigate signals before calling them findings.

Focused helper agents follow up on candidate weaknesses. Confirmed vulnerabilities, informational observations, and disproven leads are tracked separately so you can judge the evidence—not just an alert label.

Test what sits behind the login.

Shared cookies and bearer tokens carry authentication context across the workflow and helper agents, supporting checks on authenticated APIs and multi-step flows instead of only the public landing page.

Know what ran—and what it found.

Watch tool execution and discovered targets in the terminal. A completed assessment leaves a readable report and a local evidence database, giving your team both the summary and the details behind it.

A question worth testing

Can one customer read another customer's records?

Your happy-path tests can prove that an order page works. An authorization test asks whether it works for the wrong account, too.

In this illustrative scenario, discovery finds /api/orders/{id}. With approved test accounts and session context, the agent can probe whether changing the object ID crosses an ownership boundary.

From a suspicious response to evidence

A promising signal becomes a candidate for helper-agent investigation. A response alone is not the conclusion: the workflow evaluates the result, records its status, and retains technical evidence for review.

What the agent does for you

One investigation, from discovery to report.

You configure the engagement. Fire Starter selects tools, carries context between phases, and investigates what it finds while you follow progress in the terminal.

1. Discover where to look

Identify exposed hosts and services to build a picture of the target rather than testing a URL in isolation.

2. Map the reachable surface

Discover routes, open ports, component versions, and headers that help the agent choose relevant checks.

3. Probe for weaknesses

Run checks for issues such as injection, broken object-level authorization, token handling, and mass assignment. Initial signals remain candidates for investigation.

4. Follow up on promising leads

Focused helper agents use the available tools and session context to investigate exploitability and refine supporting evidence.

5. Give your team a reviewable handoff

Summarize confirmed findings and informational observations in Markdown. Preserve execution logs and technical finding records in SQLite for deeper review.

What it tests

Look beyond the bugs your functional tests catch.

Challenge access controls, untrusted inputs, sessions, and exposed services with built-in security checks. The agent selects techniques based on the target and available context.

Authorization and logic

  • BOLA, BFLA, and IDOR validation paths
  • Mass assignment and business-logic bypass checks
  • Rate-limit probing & assessment confidence modules

Web and API input abuse

  • SQL, NoSQL, XPath, LDAP, and command injection modules
  • GraphQL introspection and schema security checks
  • HTTP verb tampering, smuggling, and parameter pollution

Session, JWT & header security

  • JWT audit (alg: none, key confusion, kid header manipulation)
  • Cookie Jar session management & auth token propagation
  • CORS, security headers, and cookie attribute analysis

Discovery and infrastructure

  • Google dorking, subdomain enumeration, and takeover analysis
  • Port scanning, component version analysis, and route discovery
  • Local privilege escalation and SSH pivot modules

Open source, under your control

Own the workflow—not another black box.

Inspect the source, add checks for your environment, and choose your model provider. Go modules and a shared knowledge graph connect the investigation; local files keep the results available after the run.

Local inference can stay inside your environment. Hosted providers receive prompt context that may include assessment data. MIT-licensed code is free; hosted model usage may incur charges.

Factory registration pattern
func init() {
    RegisterModule("my_module", func(payload map[string]any, onLog func(string)) (ExecutableModule, error) {
        target := PayloadString(payload, "url", "http://127.0.0.1")
        module := &MyModule{Target: target}
        return ModuleWrapper{
            Module: module,
            ExecuteFunc: func(ctx context.Context) (any, error) {
                return module.Execute(ctx)
            },
        }, nil
    })
}

Architecture overview

Flags and config are loaded in cmd/fire_starter/main.go. The agent workflow in src/agent/workflow.go initializes the provider, scores tools, manages target progression, and drives helper sub-agents. The executor in src/matrix/real_executor.go resolves techniques to registered module factories under src/modules/core, while src/matrix/knowledge_graph.go and src/matrix/db.go retain evidence and manage vulnerability lifecycles in fire_starter.db.

Adding a new built-in check

Current runtime support is centered on the built-in registry in src/modules/core.

1
Define the technique Add metadata in src/matrix/decisions.json.
2
Implement the module Create the Go implementation in src/modules/core/.
3
Register and test Register it with RegisterModule and add _test.go coverage.
